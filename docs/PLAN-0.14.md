## 1. 伤害预估：从"数字"到"数字 + 原因"

### 1.1 问题不在数字，在归因

0.13 已经给了"预计 3×6 ≈ 18 伤害"。但玩家真正的困惑是：

> 我卡上写 18，为什么打上去只有 2？

因为对面是**白噪唱诗班**：`Resistance 9`。规则层的减免是 `min(raw × 75%, 抗性)` ——
18 点原始伤害被砍掉 9 点，剩 9；而如果是文心那种低伤害武器，直接落到保底 1 点。

**玩家看到的是"18"，打出的是"2"，中间那 16 点去哪了，游戏一个字都没说。**

这在设计上是最糟的一类：**不是数值错，是解释缺失**。玩家不会归因到"抗性"，只会归因到"这游戏坏了"。

### 1.2 做法：把抗性和结果摆在同一个句子里

敌人名牌现在是四行：

```
        白噪唱诗班
   ████████████░░░░
   甲 0 · 抗 9 · 受 2      ← 新增
   白噪咏叹 → 天秤 2×4      ← 原有的意图预告
```

三个信息一次到位：
- **抗 9** —— 它是反技术单位（`Resistance ≥ 7` 时整行变橙色）
- **受 2** —— 你当前选中的技能打上去就是这个数
- 换一把物理武器，这一行会立刻变成别的数字

**动的不是数值，是归因路径。** 玩家从"游戏坏了"变成"我该换武器"。

> 参考 Slay the Spire 的 Intent 与 Into the Breach 的完整攻击预告：这两款游戏的共识是
> **把结果提前告诉玩家，游戏不会变简单，只会变公平**。
> 本作 0.13 已经做了意图预告，这一批补上了"伤害归因"这最后一块。

### 1.3 顺带发现：描述里的百分比是命中率，不是伤害倍率

查数据时发现的：全表 13 个 `dice = 2` 的玩家技能，描述写的是"造成 2 次 75% 物理伤害"，
而 `accuracy` 字段正好是 75。**那个百分比是命中率**。

例子：

| 技能 | 描述原文 | 实际 dice × damagePerDie | accuracy |
|---|---|---|---|
| 罪证标记 | 造成 2 次 **75%** 物理伤害 | 2 × 3 | 75 |
| 终审判决 | 造成 2 次 **80%** 物理伤害 | 2 × 4 | 80 |
| 双生采样 | 造成 2 次 **78%** 技术伤害 | 2 × 4 | 78 |

不改 78 条手写文案（改文案容易改出语病，且战斗中玩家看的是卡片不是百科），
而是在卡片上把三件事写全：

```
2 次 × 3 ≈ 6 伤害 · 命中 75% · 期望 5
```

**"期望"这个词很重要**：命中 75% 意味着长期平均只中 1.5 次。原来只写"6 伤害"，
玩家会按满命中做规划，然后在关键时刻被 25% 的落空打崩心态。

### 1.4 实现要点

| 位置 | 做什么 |
|---|---|
| `app.js` `basicSkillOf(u)` | 普攻也当成一个"技能对象"（`accuracy` 取 `weaponAccuracy`），技能卡和预估共用一份定义 |
| `app.js` `forecastAgainst()` | 复刻规则层公式：`raw = dice × perHit`，`减免 = min(raw × 75%, 护甲或抗性)`，命中保底 1 点 |
| `app.js` `applyDamageForecast(c)` | 把结果挂到 `combat.units[].forecast`（前端临时字段，不进存档、不回传服务端） |
| `battle3d.js` | 名牌新增 `甲/抗/受` 行；`updateUnits` 比较 `forecastTotal` 决定是否重绘 |

> 为什么挂在 unit 上而不是传参：3D 层的 `render()` 已经拿到整个 `combat`，
> 再开一条参数链会把 drawPlate / createUnit / updateUnits 全部污染。
> 前端状态本来就不会被序列化回服务端（`grep JSON.stringify(S.game)` 零命中），所以安全。

## 2. 幕间整备：打完首领的那一分钟，本来就该配装

### 2.1 问题：最该花钱的时刻，游戏把钱包锁了

原来幕间（`GamePhase.ActTransition`）的界面只有一个按钮：**进入下一幕**。

而强化只在安全屋、换装虽然随时能做但要先关掉幕间弹窗（而 `syncModals()` 会立刻把它弹回来）。
结果就是：

> 打完首领 → 拿到 60 记忆币 + 合金 → 看着"进入下一幕" → 带着没花的钱进了下一幕。

这不是"设计选择"，是**流程上的死角**：玩家刚经历完一场硬仗、刚拿到奖励、刚好知道下一幕是什么主题
——这是整局游戏里**信息最充分、最该做构筑决策的 30 秒**，却被一个单向按钮跳过了。

### 2.2 做法：幕间变成三个页签

```
[ 情报 ] [ 强化 ] [ 换装 ]
```

- **情报**：原有内容（本幕结算、下一幕目标、奖励说明）
- **强化**：复用安全屋的 `gearUpgradeRowsHtml`（同一份代码，两处调用，不会漂移）
- **换装**：左槽位 + 右背包，点击即穿，属性立刻重算

后端只改了一处：`ApplyActionCore` 的 `ActTransition` 分支原来一刀切
`throw new GameException("请先进入下一幕。")`，现在放行 `equip` 和 `upgrade`：

```csharp
// 幕间整备：换装和强化放行——刚打完首领是最该配装的时刻
if (action.Type is not ("equip" or "upgrade"))
    throw new GameException("请先进入下一幕。");
```

`Upgrade` 自己的相位检查也同步放开：

```csharp
if (state.Phase is not (GamePhase.Safehouse or GamePhase.ActTransition))
    throw new GameException("只能在安全屋或幕间强化装备。");
```

### 2.3 为什么不是"直接开放所有动作"

幕间是个**过渡态**，玩家还没有行动力、没有当前行动者。
如果放开移动/交互，会出现"在幕间走进节点"这种状态机漏洞。

所以只放行**两类幂等的整备动作**：换装、强化。它们不改地图、不改回合、只改自己的数值。

> 这条边界值得写进约定：**过渡相位只放行"只影响自己"的动作**。

## 3. 验证

| 项 | 结果 |
|---|---|
| `DataAudit` | **83/83**（新增 2 条：探索期拒绝强化、幕间允许强化并扣费） |
| `forecast-probe`（新增探针） | 逐个技能读名牌预估：拳套 9 / 罪证标记 6 / 终审判决 8 → **PASS 预估随技能变化** |
| 数值一致性 | 截图核对：卡片 `2 次 × 3 ≈ 6` ↔ 名牌 `受 6`，逐字一致 |
| 真机 `browser-e2e` | 1/2/3/4 人通关三幕，`failures: []`（幕间会自动切三个页签并实测一次强化） |

### 3.1 探针踩到的坑（值得记）

`forecast-probe` 第一版对所有技能都读出 18，差点误判成"预估链路坏了"。真实原因是：

> **点技能会 `renderCombat()` 重建整块 innerHTML，上一轮拿到的 DOM 节点会脱离文档树。
> 点一个不在文档里的节点，事件不会冒泡到 `document`，委托处理器收不到。**

所以探针必须**每轮重新查询 DOM**。这类"探针自己坏了、却看起来像被测系统坏了"的坑，
比真 bug 更危险——它会让人去改本来没问题的代码。

## 4. 第五批：把上一批列进"还没做"的三项收掉

### 4.1 换装属性 diff（做了）

原来背包里只能看两件装备的绝对值，判断"这件比那件强多少"要自己心算。
现在每件备选装备下面直接写**相对当前装备**的差：

```
备用心脏 +0             HP +20 · VIT +5
                          HP +20  VIT +5   [装备]
穿甲狙击枪 +0       武器 2×7 命中65% → 3×4 命中80%   [装备]
```

- 数值类走差值（绿色加、红色减）
- 武器是"替换"不是"加减"，所以单独写 `旧 → 新`，用中性色

实现：`gearDeltaText()` / `gearDeltaHtml()` / `bagItemHtml()`，
背包面板和幕间换装**共用同一份**（这两处原本是复制粘贴的两段 HTML，这次合并了）。

### 4.2 文案统一改写（23 处，做了）

```
造成 2 次 75% 物理伤害   →   造成 2 次物理攻击（命中 75%）
```

全表 23 处一次性改完，零残留，并加了永久断言：

```csharp
Ok("技能描述不再把命中率写成「X% 伤害」", bad.Count == 0, ...);
```

### 4.3 幕间复活：**我没做，因为它已经存在**

这条要单独说清楚，因为它是一次"需求本身有问题"的判断。

原本的计划是"幕间也允许花 60 记忆币 + 1 队伍生命复活队友"。但翻 `AdvanceAct` 时发现：

```csharp
p.Downed = false;
p.Hp = wasDowned ? Math.Max(1, p.MaxHp * 40 / 100)   // 倒下的以 40% 生命归队
                 : Math.Max(p.Hp, (int)Math.Ceiling(p.MaxHp * 0.7));
```

**幕间本来就会自动把所有人拉回来**：倒下的 40% 生命、活着的至少 70%，
而且**不花记忆币、不消耗队伍生命**。

所以再加一个"花 60 记忆币复活"的按钮，不是新功能，是**功能倒退**——
玩家会看着一个比免费方案更贵的按钮，而屏幕上的说明还在告诉他"倒下成员重新上线"。

**改成了信息透明**：幕间情报页会把这条规则明写出来 ——

> **会自动归队**
> 鲸落 会在进入下一幕时以 **40% 生命**自动上线——不消耗记忆币，也不消耗队伍生命。

> 教训：需求写着"加一个 X"，先确认"X 现在有没有"。这次如果有求必应地加按钮，
> 结果会是**游戏变差、代码变多、玩家更困惑**。

## 5. 还没做

| 项 | 为什么先不做 |
|---|---|
| 技能卡的"对当前目标"精确值 | 选目标即释放，没有"选中目标但不放"的中间态；名牌上的"受 X"已经覆盖了这个需求 |
| 幕间批量换装（一次换一整套） | 现有单件换装 + diff 已经够用，批量是效率优化不是体验缺失 |
| 装备对比的"期望收益"（把命中/伤害折算成 DPS） | 会把简单问题复杂化，玩家看 diff 比看 DPS 更直观 |
