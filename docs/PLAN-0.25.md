> **历史文档，仅作背景。**
> 当前实现状态、验收数字与已知限制一律以 [`HANDOFF.md`](../HANDOFF.md) 和 [`README.md`](../README.md) 为准；
> 本文描述的是当时的计划或审计快照，其中的版本号、文件路径和行为可能已经变化。

> **For RouterCode:** Use `subagent-driven-development` skill to implement this plan task-by-task. 每个任务完成后必须运行对应验证；未经用户明确确认，不得修改代码、删除文件、重置存档或提交 git。

**目标：** 将当前“系统很多、流程可通关的 Demo”提升为一款具有清晰新手体验、明确重复游玩动机、强角色协同、可记忆事件、差异化 Boss 和有价值失败反馈的完整 Web 合作战术 Roguelike。

**项目基线：** `D:\AGI2046`，当前服务 `http://127.0.0.1:5178`，服务版本接口返回 `0.19.3`。

**技术栈：** .NET 10 / C# 规则层与 ASP.NET Core 服务端；原生 HTML/CSS/JavaScript；Three.js 战斗表现；文件 JSON 存档；Node.js 自动化检查；现有 `tools/audit`、`tools/e2e`、`tools/smoke`、`tools/ui` 测试脚本。

**重要约束：**

1. 保留当前三幕、1–4 人合作、六角战斗、d100、电子追踪、觉醒、支线、联机房间、剧情/VN/CG 的主干。
2. 不以继续增加节点数量、立绘数量或特效数量作为主要目标。
3. 所有新增规则必须能在 UI 中解释；所有影响胜负的随机结果必须可追溯。
4. 优先移动端 390×844，再兼容桌面。
5. 所有新系统默认可关闭、可降级或可跳过，不能阻塞主流程。
6. 每个阶段都必须可单独发布；不允许把全部风险积累到最后一次合并。

## 1. 当前问题判断

### 1.1 产品层问题

当前项目的功能覆盖已经较广，但核心体验仍有四个断点：

- 玩家不知道“此刻最重要的事情是什么”；
- 角色很多，但选择角色没有形成足够明显的战术差异和组合关系；
- 通关/失败后，再开一局的理由不足；
- 事件、Boss 和失败没有充分改变玩家的决策和记忆。

### 1.2 本计划不解决的问题

以下事项暂不作为本计划的第一阶段目标：

- 继续制作大量静态美术资产；
- 引入 Unity 或重写当前 Web 宿主；
- 把 HTTP 轮询改成 WebSocket；
- 添加账号体系、云存档或商业化；
- 重做全部数值；
- 一次性制作 96 张全新角色差分；
- 把游戏扩展成开放世界或 MMO。

### 1.3 目标用户体验

新玩家在前 20 分钟内应能回答：

1. 我们的最终目标是什么？
2. 当前这一轮最应该做什么？
3. 为什么选择这个角色？
4. AP、Focus、电子追踪和队伍生命分别有什么用？
5. 什么时候应该战斗、休息、购物或撤离？
6. 我怎样帮助队友，而不是只操作自己的角色？

老玩家在完成一局后应能回答：

1. 这局为什么成功或失败？
2. 我这次尝试的构筑是什么？
3. 下一局我要换什么策略？
4. 这局是否解锁了新内容、情报或挑战？

# 2. 产品目标与验收指标

## 2.1 版本目标

建议分成以下版本，而不是直接追求“大版本全部完成”：

| 版本 | 主题 | 核心产出 |
|---|---|---|
| 0.20 | 可理解 | 新手教学、任务面板、术语解释、目标提示、首局节奏修整 |
| 0.21 | 可重玩 | 挑战模式、规则变异、通关评级、失败复盘、解锁记录 |
| 0.22 | 有协作 | 角色协同、联合作用、多人专属事件、资源请求/支援 |
| 0.23 | 有记忆 | 分支事件、持久情报、角色关系、事件后果、章节回顾 |
| 0.24 | 有辨识度 | 三个差异化 Boss、构筑化装备、结局条件、完整平衡回归 |
| 0.25 | 成品打磨 | 无障碍、移动端、性能、文案、存档迁移、发布验收 |

## 2.2 可量化验收指标

### 新手体验

- 首次玩家在不阅读外部文档的情况下，20 分钟内完成教学战斗；
- 教学期间必须完成：移动、普通攻击、主动技能、结束回合、查看敌方意图、使用一次资源、一次安全撤退；
- 关键术语首次出现时，玩家可在一键内查看解释；
- 前 30 分钟不出现“玩家不知道下一步要做什么”的空状态；
- 教学失败后可以重试，不删除正式存档。

### 重玩体验

- 每局至少生成 2 个可见的规则变异；
- 同一角色至少有 2 种可行构筑；
- 终局页面显示本局构筑、关键选择、失败原因和下一局建议；
- 通关后至少提供 3 种下一次尝试方向；
- 变异不应让某些角色或技能完全失效。

### 合作体验

- 每名角色至少拥有 1 个能明显帮助队友的动作或效果；
- 四人局中至少有 3 类行动会影响其他玩家的决策；
- 多人事件至少有 3 个需要讨论/投票/分工的节点；
- 单人热座模式仍可完成，不依赖第二个真实玩家。

### 质量

- `dotnet build src/AGI2046.Server/AGI2046.Server.csproj --no-restore` 0 警告、0 错误；
- 既有 `api-probe`、`systems-check`、`room-check`、`resume-check`、`cg-check` 全部通过；
- 新增规则必须有规则层自动化覆盖；
- 390×844 无横向溢出；
- 所有新增剧情和 UI 文案均有中文、英文 key 或明确的当前单语策略；
- 用户不得在未经确认的情况下丢失存档。

## 4.1 任务 A：定义新手教学状态

**目标：** 增加一个不污染正式 Roguelike 随机流程的 Tutorial 模式。

**文件：**

- 修改：`src/AGI2046.Rules/Models.cs`
- 修改：`src/AGI2046.Rules/GameEngine.cs`
- 新增：`src/AGI2046.Rules/TutorialEngine.cs`
- 修改：`src/AGI2046.Server/Program.cs`
- 修改：`web/js/app.js`

**设计：**

新增以下概念：

- `GameMode`: `Standard / Tutorial / Challenge`
- `TutorialStep`: `Intro / Move / Attack / Skill / EndTurn / EnemyIntent / Resource / Retreat / Complete`
- `TutorialState`: 当前步骤、是否允许跳过、已完成动作、教学提示、是否首次玩家；
- `GameState.Mode`；
- `GameState.Tutorial`。

**规则要求：**

1. 教学使用固定 2 名角色和 1 个低威胁敌人；
2. 教学中不生成正式三幕地图；
3. 教学完成后进入正式新局，而不是把教学数据混入正式存档；
4. 教学失败可重试；
5. 已完成教学的玩家可以在标题页关闭；
6. 教学必须支持 1 人热座，不要求真实联机。

**TDD 步骤：**

1. 在 `tools/smoke/tutorial-check.mjs` 写失败测试：创建 Tutorial 模式，验证初始步骤和允许动作；
2. 运行 `node tools/smoke/tutorial-check.mjs`，预期失败；
3. 添加模型和最小状态推进逻辑；
4. 再运行脚本，确认初始步骤和步骤转移通过；
5. 添加非法动作测试，例如在未移动前不能直接跳到结算；
6. 运行 `dotnet build ...` 和 Tutorial smoke。

## 4.2 任务 B：制作固定教学流程

**目标：** 将教学控制在 10–20 分钟，解释完整核心循环。

**文件：**

- 新增：`src/AGI2046.Rules/GameData.Tutorial.cs`
- 修改：`src/AGI2046.Rules/TutorialEngine.cs`
- 修改：`web/js/app.js`
- 修改：`web/index.html`
- 修改：`web/css/style.css`

**固定流程：**

1. 介绍任务：关闭信标，电子追踪会推进；
2. 选择一个角色；
3. 移动到相邻节点；
4. 进入小战斗；
5. 选择普通攻击；
6. 选择一次主动技能；
7. 查看敌方意图；
8. 结束回合；
9. 使用一个消耗品或获得一次资源；
10. 教学演示撤退条件；
11. 完成战斗；
12. 进入安全屋并说明恢复；
13. 结束教学，展示“标准模式”入口。

**验收：**

- 每个步骤都有可见目标；
- 未完成步骤时，错误提示明确说明“先做什么”；
- 教学不会出现随机地图阻塞；
- 教学结束后保存 `tutorialCompleted=true`，但不写入正式对局；
- 关闭教学后可从标题页重新打开。

# 5. 阶段二：0.21“可重玩”

## 阶段目标

给每一局增加有意义的差异，并让失败转化为信息，而不是单纯丢失数小时进度。

## 5.1 任务 F：挑战模式模型

**文件：**

- 修改：`src/AGI2046.Rules/Models.cs`
- 新增：`src/AGI2046.Rules/ChallengeEngine.cs`
- 新增：`src/AGI2046.Rules/GameData.Challenges.cs`
- 修改：`src/AGI2046.Server/Program.cs`
- 修改：`web/js/app.js`

**数据结构：**

```text
ChallengeRun
- ChallengeId
- Seed
- MutatorIds
- Difficulty
- ScoreMultiplier
- StartedAt
- CompletedAt
- Result
```

**首批 12 个规则变异：**

1. `追踪加速`：电子追踪推进速度提高；奖励提高；
2. `资源匮乏`：商店价格提高，事件奖励提高；
3. `冷却失控`：主动技能冷却 +1；
4. `玻璃队伍`：最大生命降低，伤害提高；
5. `敌意协议`：敌方意图更危险但奖励提高；
6. `无安全屋`：部分安全屋替换为特殊事件；
7. `过热武器`：连续使用同一技能会增加风险；
8. `镜像敌人`：敌方复制最近一次玩家技能；
9. `少数派`：队伍上限降低，但经验提高；
10. `反囤积`：消耗品不能跨幕保留；
11. `深层觉醒`：觉醒更强但节点更危险；
12. `全局故障`：每幕随机关闭一种节点类型。

**设计约束：**

- 每个变异必须有说明、风险、奖励和适合的策略；
- 不允许纯粹隐藏惩罚；
- 变异必须能在开局前预览；
- 变异组合需要经过自动模拟；
- 不允许变异让某一角色永久不可用。

## 11.2 平衡仪表盘

- 各角色通关率；
- 各角色出场率；
- 各技能使用率；
- 各装备选择率；
- 平均战斗轮数；
- 平均电子追踪剩余；
- 撤退率；
- 死亡原因；
- 各变异胜率；
- Boss 阶段平均持续轮数。

警戒线建议：

- 单角色标准模式出场率不超过 45%；
- 单角色通关率不低于最低角色通关率的 60%；
- 单个技能使用率不超过同类技能平均值的 2.5 倍；
- 任何挑战变异不能导致全队伍通关率低于 5%，除非明确标注为极限挑战；
- Boss 二阶段不能平均在 1 回合内结束；
- 协同触发应实际发生，但不能成为唯一通关方式。

# 13. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 系统继续膨胀 | 高 | 每阶段只交付一个核心体验，不新增无关节点 |
| 新手教程变成强制长剧情 | 中 | 每步可跳过，完成后关闭；只教学必要规则 |
| 挑战变异破坏平衡 | 高 | 自动模拟 + 固定种子 + 变异预览 + 可禁用 |
| 多人投票阻塞 | 高 | 超时默认、掉线自动 ready、房主兜底 |
| 协同系统增加复杂度 | 高 | 先做 8–12 个可组合效果，不做全角色专属大系统 |
| Boss 机制不易理解 | 高 | 战前预告、战斗内状态卡、行动记录、失败复盘 |
| 存档字段变化导致丢档 | 极高 | 版本迁移、原文件备份、隔离过新格式 |
| 移动端空间不足 | 高 | 390×844 优先、信息分层、折叠面板、避免常驻大卡 |
| 现有回归被破坏 | 高 | 每个任务跑完整 smoke；不允许最后集中修回归 |
| 叙事内容制作量过大 | 中 | 先文字和状态后美术；复用现有 VN、key art、图标 |
| 规则层缺乏测试 | 高 | 新增规则先写 smoke/probe，再接 UI |

# 15. 最终完成标准

只有满足以下条件，才可称为“成品化阶段完成”：

- 新玩家能在不读外部文档的情况下完成教学并开始标准局；
- 标准局和挑战局的差异对玩家可见；
- 玩家能从复盘中理解失败原因；
- 至少 8 个角色组合能产生明确战术差异；
- 至少 6 个事件会产生跨节点或跨幕后果；
- 三个 Boss 的核心决策完全不同；
- 装备能形成至少 5 种可识别构筑；
- 多人玩家能进行资源、支援或投票协作；
- 失败不会只意味着“这局白打”；
- 旧存档可安全迁移；
- 全部核心流程在桌面和移动端可完成；
- 关键规则有自动化验证；
- 已确认的群体技能骰子动画问题得到修复或被明确降级为非阻塞问题；
- README、HANDOFF、版本号和实际服务版本一致。

# 16. 下一步执行入口

实施前必须先确认三个产品决策：

1. 是否接受 Tutorial 作为 0.20 的第一优先级；
2. 挑战模式是否允许永久解锁内容，还是只提供情报/称号/外观；
3. 多人协作优先做支援动作，还是优先做投票事件。

默认建议：

- 先做 Tutorial + 当前目标面板；
- 解锁内容以情报、称号、外观和新变异为主，不提供永久数值优势；
- 先做支援动作，再做投票事件；
- 所有代码实施前先建立测试，再修改规则层；
- 所有文件修改、存档迁移和删除动作先向用户确认。
